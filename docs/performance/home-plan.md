# FitBite 首页请求与计划锁压测

2026-11-25 在同一台 ARM64 主机上比较了基线 `459e68b` 与本报告所在提交。32 个并发客户端下，首页数据加载 P95 从 737 ms 降到 87 ms。针对已发布训练计划，Redis 缓存未命中且另一事务持有用户行锁时，432 次请求均在写锁释放前返回。两项实验独立运行。[逐轮数据](home-plan-results.json) · [复现步骤](../../scripts/perf/README.md)

## 首页

按已登录且已有计划的会员首次进入首页计数。用 React 挂载两个版本的页面和数据上下文，记录它们对 API 的调用。旧版触发 19 次训练计划、16 次完成记录、4 次资料和 5 次其他读取，共 44 次。新版读取用户资料、当天训练、当天训练完成状态和 16 天打卡标记，各 1 次。点击历史日期才读当天的训练和完成状态，打开饮食或进度页才加载各自数据。

随后用实际鉴权 HTTP 请求重放两组调用。计时从客户端开始发请求到最后一个响应读完并验证，涵盖服务端和本机网络。旧界面的定时器等待、真机渲染、蜂窝网络和登录均不在计时内。

| 首页指标 | 优化前 | 优化后 |
|---|---:|---:|
| 每次访问的 HTTP 请求 | 44 | 4 |
| 平均每次访问的 MySQL SELECT | 82.06 | 5.91 |
| 平均每次访问的响应体 | 130.8 KiB | 2.0 KiB |
| P50 | 492 ms | 38 ms |
| P95 | 737 ms | 87 ms |
| P99 | 922 ms | 134 ms |
| 每秒完成首页访问 | 63.0 | 732.5 |
| 三轮完成访问数 | 5,717 | 65,782 |
| 三轮失败访问数 | 0 | 0 |

每个版本运行三轮，每轮持续 30 秒，32 个并发客户端连续完成访问。旧新版的顺序按轮交替为旧新、新旧、旧新。上表延迟和速率取各轮对应指标的中位数。每次访问的 SELECT 来自 MySQL Performance Schema 中该库 SELECT 计数的增量除以当轮完成访问数，响应体按未压缩 HTTP 正文字节计。该并发档位的首页吞吐达到原来的 11.6 倍，生产容量还取决于用户数、网络、缓存命中率、写入占比和数据库部署。

### 等功能对照

固定用户要看到「当天训练计划」和「七天热量」。旧客户端为取得这些数据预取 17 天计划，并通过 1 次资料和 14 次按日完成记录请求算出图表。新版请求当天计划和七天热量各 1 次。热量接口用一条按日期分组的 SQL 同时算出已完成饮食和训练的热量，补齐没有记录的日期，保留原来的基础代谢计算规则。双方均检查训练计划条数以及每天的热量，另有回归测试覆盖空日期、未完成项目及用户隔离。

|---|---:|---:|
| 两项功能合计 HTTP 请求 / 访问 | 32 | 2 |
| 两项功能合计 MySQL SELECT / 访问 | 60.31 | 2.94 |

同一固定次数设置也重放了完整首页，旧新版 P95 分别为 416.01 和 100.37 ms。固定次数实验每轮较短，持续负载结果用于评价首页吞吐。

## 数据库锁

已发布的训练和饮食计划在 Redis 未命中时直接查询 MySQL。只有确实查不到计划时，才开启短事务，锁定用户、再次查询并生成。Redis 缓存键带用户级版本，避免较早发起的读取在计划更新后回填旧内容。重新生成提交后才使版本失效，事务回滚保留原缓存。代价是热缓存读取增加一次 Redis 版本读取。发布时先切换后端写流量，再发布调用新热量接口的移动端。旧后端修改计划时只清理旧缓存键，在并行处理写请求时无法使新版版本键失效。

| 同一会员，四轮交叉对照 | 优化前 | 优化后 |
|---|---:|---:|
| 6 个热缓存计划读取、2 个并发打卡，读取 P95 | 9.52 ms | 7.94 ms |
| 同场景，打卡 P95 | 14.32 ms | 11.63 ms |
| 同场景，InnoDB 行锁等待次数 / 累计时间 | 72 / 121 ms | 72 / 132 ms |
| 受控持锁 100 ms、读已发布且缓存未命中的训练计划，读取 P95 | 112.18 ms | 10.54 ms |
| 同场景，在解锁前返回的请求 | 0 / 432 | 432 / 432 |
| 同场景，InnoDB 行锁等待次数 / 累计时间 | 432 / 44,280 ms | 0 / 0 ms |

每轮每种场景运行 18 波。在普通读写场景，每波校验两次打卡恰好新增一条记录，重复打卡返回同一记录 ID。各轮延迟分布有重叠，写写竞争仍在，无法由此推断一般写吞吐明显提高。受控场景每波只清理该会员当天的计划缓存，独立事务持有用户行锁，再并发发出 6 个训练计划 GET。对两版均核对计划 ID 及顺序。锁压测共 2,016 次计时 HTTP 请求，全部成功。饮食计划同样的持锁读取行为由独立集成测试验证。

## 环境与复现边界

- 首页服务使用 Spring 生产配置、JDK 21、384 MiB 固定 JVM 堆、Hikari 最大 20 个连接。实际运行 MySQL 8.0.44（InnoDB，REPEATABLE READ，256 MiB 缓冲池）和 Redis 7.2.7。两个版本读取同一份专用首页数据库。32 个合成账号有 90 天历史，共 17,280 条完成记录、1,632 条训练计划明细、2,848 条打卡记录。
- 首页每次切换版本都重启应用并重置专用 Redis 库。开始计时前先登录、串行预热受保护路径，然后再完成 64 次预热访问。每个虚拟用户复用最多 6 个 HTTP 连接。锁实验使用分别初始化的 MySQL 库和 Redis 逻辑库，计时不与首页负载重叠。
- 基线在首次并发预跑中出现过 HTTP 500。堆栈为 `JwtUtil.validateToken → DefaultJwtParserBuilder.build → ServiceLoader`，异常为 `NoSuchElementException`。两版正式对照统一采用预热流程。上述零错误覆盖正式计时阶段，后续已单独修复并复测了[JWT 并发冷启动](jwt-startup.md)。

最终后端构建通过 44 项测试，包含真实 MySQL 和 Redis 的并发集成用例。移动端 9 项自动测试通过，Android 与 iOS 均完成生产模式 Hermes 资源导出。
