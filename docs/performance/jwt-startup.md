# FitBite JWT 冷启动对照

2026-11-25 使用 JDK 21、真实 MySQL 8.0.44 和 Redis 7.2.7，在本机对比基线 `42d5ec2` 与本报告所在提交。每轮都重启应用进程，匿名健康检查首次返回 UP 后立即发送第一批业务请求。每位会员均保有独立身份，每个 200 响应都核对账号 ID 和用户名。[逐轮数据](jwt-startup-results.json) · [复现步骤](../../scripts/perf/README.md#jwt-冷启动对照)

已有令牌场景中，每轮第一批结束后，同样 32 位会员立即发第二批读取。旧版共成功 320 / 320 次，新版 320 / 320 次。首次登录场景的后续读取只使用成功登录后实际取得的令牌。两类首批的 500 数和成功请求延迟分别统计，避免快速返回的错误拉低延迟。已有令牌场景中，旧版出错的 5 轮都记录到了 JJWT 解析器查找 JSON 提供者的堆栈。首次登录场景中，旧版有 1 轮记录到签发时查找 JSON 提供者的堆栈。新版首次登录的成功请求 P95 在这四轮高约 25 ms，观测到的改善主要是首批成功率。

## 修改

旧版为每次受保护请求构造 JWT 解析器，有效令牌从头解析两次。JJWT 0.12.3 的默认实现会在构造解析器时查找 JSON 反序列化器，先前的并发首访 500 出现在这条路径。现在 Spring 构造 `JwtUtil` 时校验签名密钥，创建可复用的解析器，并为签发和验签显式配置现有的 Jackson 编解码器。每次签发使用独立的构建器，每个带有效令牌的请求只验签一次并继续查询数据库中的最新身份。JJWT 官方接口明确说明构建完成的解析器可被多线程共享。[JwtParserBuilder 源码](https://github.com/jwtk/jjwt/blob/0.12.3/api/src/main/java/io/jsonwebtoken/JwtParserBuilder.java#L768-L773)

回归覆盖 HS256、HS384、HS512 三种现有密钥长度的新旧令牌互通，以及过期和坏签名、用户降权、账号删除、并发签发和解析。签名密钥过短会在应用启动时被拒绝。

## 方法和适用范围

- 已有令牌访问使用 10 对全新 JVM，首次登录使用另 4 对。每个进程只接收一批 32 个并发的首访，客户端使用独立 HTTP 连接。每对轮换新旧版执行顺序，JVM 堆均固定为 384 MiB，Hikari 最大连接数 20。压测与完整回归分开执行。
- 每个场景先在独立的旧版进程中走真实的注册和登录，准备 32 个测试会员，读取各自的资料后关闭该进程。两版共用同一签名密钥、MySQL 与已经缓存的会员资料。计时进程在首批前只接收匿名健康检查，未用令牌、登录或资料请求预热鉴权。
- 表中成功数和失败率按所有轮次合计。首批 P95 取各轮成功请求 P95 的中位数，就绪耗时取对应各轮的中位数。登录耗时包括密码校验，资料读取包括鉴权、身份查询、资料缓存与本机 HTTP 往返。本次验证的是应用进程冷启动，数据库与 Redis 在实验中持续运行。
