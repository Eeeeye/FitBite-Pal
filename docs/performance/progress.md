## 为什么能少读数据库

旧版手机并发读取体重、实时热量、综合统计及当天餐次，鉴权会为每个请求读取一次身份。体重和统计又会各读一遍会员资料及同一段打卡记录。新版的 `GET /data/progress` 在一次鉴权后读取四份业务数据，分别为窗口内打卡、每日最新热量快照、按天聚合的饮食与运动完成数据，以及客户端当天的餐次索引和勾选状态。本人查询复用本次鉴权已经取得的会员，管理员代查单独读取目标会员。旧 API 继续可用，发布时先更新后端，再更新移动端。

同一天存在多条历史热量快照时，取最大 ID。开发中用 MySQL `EXPLAIN ANALYZE` 检查去重 SQL，发现只在子查询限定会员和日期会导致外层扫描全部 2,496 条快照。补齐外层条件后，同一会员和七天窗口下，内外层都命中已有的 `idx_calorie_user_date`，各读取 7 条，最后返回 6 天。这个对照用于核验新版 SQL 的访问范围。

## 怎样比较

- JDK 21、MySQL 8.0.44、Redis 7.2.7，Spring 生产配置，JVM 堆固定 384 MiB，Hikari 最大 20 个连接。两版共用相同的合成数据，包括 90 天历史、17,280 条完成记录、2,848 条打卡和 2,496 条热量快照。保留历史空体重、重复快照、缺少快照的日期和未完成的餐次，会员之间的体重、基础代谢和活动量各不相同。
- 先用旧版服务保存每位会员的完整页面数据。旧版四个接口并发返回后，按原移动端规则将餐次整理成索引到布尔值的映射。两版在每次计时访问中均对返回数据逐字段断言。额外用旧版采集了客户端日期早一天、晚一天的结果，比对新版在边界处同时保留服务器日期与客户端日期的语义。
- 每版四轮，每轮重启应用、清空该实验专用 Redis 逻辑库、完成预热，再以 32 个并发客户端持续采样 20 秒。版本顺序按轮交替为旧新、新旧、旧新、新旧。每个客户端最多复用 6 条 HTTP 连接。MySQL 由该实验独占，从全局 `Com_select` 增量取每次访问平均查询数。
- 表中 P50/P95/P99 和速率均为四轮对应指标的中位数，总访问数按轮相加。计时覆盖从发起 HTTP 到读完并比对整个页面的数据。每轮的旧版 P95 在 123.0–129.9 ms 之间，新版在 46.3–57.6 ms 之间。真机渲染、外网及生产流量不在此次采样范围内。

## 回归验证

后端完整 Maven 构建通过 53 项测试，移动端 14 项自动测试通过。React 组件挂载时验证了首次打开与点重试均只发 1 个请求，首次失败会显示中英文提示，刷新失败会保留上次成功的数据。旧账号迟到的响应以及等待期间发生的餐次勾选也已覆盖。Android 和 iOS 均完成生产模式的 Hermes 资源导出。真机安装和渲染耗时未纳入本次验证。
